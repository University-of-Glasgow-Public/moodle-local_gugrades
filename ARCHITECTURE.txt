local_gugrades plugin notes
===========================

Purpose
-------
MyGrades stores and presents grade information for Moodle courses. It adds
course grade workflows, regulation-specific handling, provisional/current
grades, conversions, administrative grades, reassessment/resit handling,
and external API endpoints used by the UI. The business logic is written
in PHP and accessible through standard Moodle web service calls. The user 
interface is a standalone Vue.js application.

Main entry points
-----------------
- classes/api.php: service-level application operations and integrity checks.
- classes/grades.php: grade records, gradebook lookups, grade trees,
  provisional/current grades, integrity checks, and resit helpers.
- classes/aggregation.php: calculates category and course results.
- classes/conversion.php: converts grades between regulation formats and tracks
  whether conversion has been applied.
- classes/regulations.php: selects the active regulation for a course.
- classes/admingrades.php: defines and validates administrative grade codes.
- classes/users.php: finds users who can be graded.
- classes/external/: Moodle webservice/external API functions.
- classes/activities/: activity-specific grade import and reading behaviour.

Aggregation performance benchmark
---------------------------------
tests/external/aggregation_performance_test.php is opt-in and uses only the
isolated PHPUnit database, reset after each case. It creates 100, 400 and 800
students, five calculated categories, twelve Schedule A assessments and two
grade revisions per assessment. Scenarios are original, from2026 single-result,
and from2026 dual-result (also with drop-low and 10% altered-weight users).
It measures initial/unchanged recalculation, page/repeated-page loading and a
single-student edit. JSON lines prefixed GUGRADES_BENCHMARK report elapsed and
database time, read/write counts, peak memory and page response bytes. Fixture
creation, assertions and response encoding are outside elapsed measurements.

Run with the existing PHPUnit installation:
GUGRADES_BENCHMARK=1 vendor/bin/phpunit local/gugrades/tests/external/aggregation_performance_test.php
Optional GUGRADES_BENCHMARK_SIZES=100 (or 100,400,800) limits case sizes.
Without the opt-in variable, these tests are skipped. There are no timing
thresholds; correctness assertions check result counts and independent streams.
In this development Compose environment (from the Moodle root):
docker compose exec -T -e XDEBUG_MODE=off -e GUGRADES_BENCHMARK=1 -w /app/html php /usr/local/bin/php vendor/bin/phpunit local/gugrades/tests/external/aggregation_performance_test.php

IMPORTANT: PHPUnit bypasses production regulation, availability, tree and
user-result caches. Repeated-page measurements are NOT warm production-cache
timings. Use the same environment and fixture for before/after comparisons,
and profile a staging request before extrapolating to live response times.
Dual and single scenarios have different optional features, so their timing
difference must not be attributed solely to dual calculation. PHP process
memory includes fixture/cache allocations and is not per-request isolation.

Initial baseline, 2026-10-14, PHP 8.3.35 / MariaDB 12.3.2 / Moodle 4.5.12+:

Scenario                      100 students    400 students    800 students
original                      5.30            39.32           131.77
from2026                      5.42            40.33           135.65
from2026-dual                  6.82            52.17           171.54

At 800 students:
Scenario          Unchanged seconds   Reads     Writes    Page seconds   Edit seconds
original          122.77              134512    24800     8.68           0.23
from2026          128.28              146512    24800     8.70           0.24
from2026-dual      162.03              188912    37601     9.23           0.31
Reads/writes above refer to unchanged recalculation, not page loading.
Page responses were approximately 1.1 MB (uncompressed JSON). The nine cases
passed 75 assertions. This is one local run, not a production SLA or a median.
Elapsed recalculation grew faster than query count; investigate PHP/framework
overhead as well as database work before attributing the scaling to SQL alone.

Low-risk aggregation optimisations
---------------------------------
Full-course aggregation loads the level-one subtree's category list once and
invalidates each student's result cache once, rather than rediscovering and
deleting the same subtree twice per student. Altered-weight existence is read
once per calculation run and passed through recursion, not cached between runs.
Page repair checks load current CATEGORY1 presence for the total and dual child
columns in one query and use keyed user/item lookups. Missing child results still
trigger full per-user repair even when parent results exist.
These changes leave grade reads/selection, duplicate repair, result writes,
audit timestamps, drop-low and regulation calculations unchanged.
Measured after this pass (same fixture/environment, one run):
- At 100 students, recalculation reads fell by 1097 in each scenario: original
  16912 -> 15815, from2026 18412 -> 17315, dual 23712 -> 22615 (unchanged runs).
- At 800 students, dual recalculation reads fell 188912 -> 180115 (4.7%).
  Writes stayed at 37601. Unchanged recalculation time was 162.87s versus 162.03s
  in the baseline; there is no demonstrated elapsed-time improvement.
- At 800 students, dual page-after-recalculation reads fell 88505 -> 87705;
  elapsed time was 9.16s versus 9.23s. Repeated-page timing varied upward.
- Single-user edit reads fell by four; grade writes remained unchanged.
The query reduction is deterministic for this fixture, but timing is noisy.
The dominant assessment reads and unconditional result writes remain for a
separately reviewed optimisation pass. Regression coverage passed 114 tests /
394 assertions; benchmark follow-ups passed four cases / 34 assertions.

Assessment bulk-read pass
-------------------------
Aggregation loads grade items and current assessment grades for its users in
two queries. A run-local snapshot is passed through recursion into usercapture;
capture still applies the same ID ordering, CATEGORY1 exclusion, provisional
selection, alert and out-of-range checks. PROVISIONAL column lookup/creation is
reused per item/points combination within that run. Normal capture-page calls
continue using individual reads. Each calculation/edit/explanation gets a fresh
snapshot; no persistent cache or latest-pointer selection replaces grade reads.
Result writes and audit behaviour are unchanged. Memory grows with current
assessment rows for the selected users (historical rows are not loaded).
Measured against the preceding low-risk pass, at 800 students in the dual
scenario, unchanged recalculation reads fell 180115 -> 151329 (16.0%).
Initial recalculation time fell 172.82s -> 167.94s; unchanged recalculation was
162.87s -> 161.17s. These single-run timings demonstrate only a modest benefit,
not a large speedup. Writes stayed at 37601 and page-read counts were unchanged.
At 100 students unchanged timings were 3.93s original, 4.03s from2026 and 5.41s
dual, versus 4.72s / 4.71s / 6.28s in the preceding pass.
The isolated 800-student process peak increased from 141 MiB to 155 MiB.
Bulk data trades additional memory for fewer queries; recordset iteration avoids
an additional flat copy of all grade rows. PHPUnit cache bypass still applies.
Regression coverage passed 116 tests / 414 assertions, with four benchmark
follow-up cases / 34 assertions. Profile SQL plans and PHP call time before
further optimisation; repeated writes/settings and test-framework overhead
remain outside this pass.

Function/SQL profiling findings (2026-10-14)
------------------------------------------
The benchmark supports optional GUGRADES_BENCHMARK_TRACE_PHASE, e.g.
unchanged_recalculation, with XDEBUG_MODE=trace. Only the selected phase is
traced; /tmp/gugrades-SCENARIO-SIZE-PHASE.xt[.gz] is reported on stdout. Traces
are limited to 100 students and suppress nested argument arrays. Xdebug tracing
has substantial overhead: use call counts/path attribution, not traced seconds
as benchmark results. Keep raw traces private (they include SQL and arguments).
Example in the development Compose environment:
docker compose exec -T -e XDEBUG_MODE=trace -e GUGRADES_BENCHMARK=1 -e GUGRADES_BENCHMARK_SIZES=20 -e GUGRADES_BENCHMARK_TRACE_PHASE=unchanged_recalculation -w /app/html php /usr/local/bin/php -d xdebug.start_with_request=no vendor/bin/phpunit --filter from2026-dual local/gugrades/tests/external/aggregation_performance_test.php

Traces of the dual scenario at 20 and 100 students identified the main cause
of superlinear PHPUnit timing:
                                      20 students       100 students
availability list loads               300               1500
fullname calls                        6020              150100
mysqli query calls                    4850              23730
mysqli query inclusive time           1.02s             5.53s
activity get_users inclusive time      10.74s            246.82s
total traced recalculation             17.42s            279.62s
Inclusive recursive timings overlap and must not be added together.

get_valid_userids() explicitly bypasses GUGRADES_VALIDUSERS during PHPUnit.
Each availability lookup consequently obtains ALL students, formats names and
initials and sorts them in activities/base.php. Five times as many students
gave about 25 times as many fullname calls. At 100 students, this path accounted
for about 88% of the instrumented request, while mysqli query execution was
about 2%. Instrumentation especially inflates paths with many small PHP calls.
Production already reuses availability lists per assessment within a request,
so this quadratic test path is NOT evidence of equivalent live behaviour.
The earlier 800-student times substantially exaggerate this availability cost.
The production cache was not disabled, enabled specially or changed for this
investigation; no new optimisation was made based on these distorted timings.

Normalised SQL totals at 100 students showed many inexpensive repeated queries:
- grade_items by ID: 4824 calls / 0.71s.
- resit existence by item: 1500 calls / 0.41s.
- course by ID: 2600 calls / 0.39s.
- role/capability checks: 1501 calls / 0.38s.
- clearing dropped flags: 1600 calls / 0.25s.
- altered-weight lookup: 1600 calls / 0.18s.
These are trace driver timings, not pure database-server execution timings.
No individual SQL family explained the superlinear growth in this fixture.
This does not rule out production slow queries or poor plans with larger
historical tables. The next reliable measurement is a staging request with
normal production caches and representative data, separately measuring a
new request/page refresh, recalculation and single-user updates. Do not infer
production elapsed time by subtracting inclusive traced costs from the baseline.

Normal-cache local course profile (2026-10-14)
--------------------------------------------
An approved local course was profiled via CLI calling the same api::recalculate
and api::get_aggregation_page functions outside PHPUnit. Existing administrator
identity was used; category results/audit timestamps were recalculated, not
assessment grades. This is NOT an HTTP/browser timing or a synthetic 800-user
load test. There were 104 gradeable users, 1664 grade-history rows and a deeper
category tree than the benchmark.
Two untraced fresh-process runs gave:
- Main top-level category: recalculation 4.71s / 4.36s; 25654 / 24886 reads,
  8321 writes. Page load immediately afterwards 0.45s / 0.46s, about 2030 reads,
  no writes, 284 KB JSON. Page loading shares warm request-local caches here.
- Empty sibling category: recalculation 0.31s / 0.27s; page 0.30s.
Process peak memory was 52-56.5 MiB. Persistent caches differed between runs.

Function trace of main recalculation confirmed 3016 availability checks but
only 29 activity user-list loads, consistent with production request caching.
1664 category-result writes and 1664 regulation option lookups were recorded.
The empty-options cache in from2026 regulation::get_options does not remember
the ordinary-course outcome; category ancestry was checked 3328 times.
The from2026 options cache now stores all outcomes (including empty arrays) by
course ID, preventing repeated ancestry queries and cross-course option reuse.
PHPUnit still bypasses cache reads so changing fixtures/configuration stays
visible within a test. Original regulations and result writes are unchanged.
After the fix, the same main-category recalculation took 4.15s with 16571 reads
(down from 24886, about 33%) and the same 8321 writes. Empty sibling reads fell
from 1373 to 853. The page still took about 0.48s. Timing is a single observation,
not a controlled speedup estimate; targeted PHPUnit validation ran concurrently
against its separate test database. A non-PHPUnit, read-only check across ten
ordinary courses verified 1000 cached lookups issued zero additional DB reads.
Focused regression tests cover empty/Engineering/Nursing cache entries, course
isolation, Engineering precedence, changing PHPUnit fixtures and aggregation:
32 tests / 208 assertions passed.
Result persistence
and first-request availability loading are also visible costs, but traced
inclusive times overlap and have large profiler overhead. SQL argument contents
were suppressed and raw traces removed after numeric summaries were saved.
These local observations must not be extrapolated directly to 800 students.

Important data
--------------
- local_gugrades_grade: grade history and current/provisional grade values.
- local_gugrades_gradesbackup: last actual grade values for each user, grade
  item and column. Written whenever a current grade is saved. Existing grades
  are copied after upgrade by the backupgrades scheduled task, in short runs
  of 500 grades. Status messages such as No grade, Grades
  missing, Cannot aggregate and Not available are omitted. Kept when MyGrades
  grades are reset, and removed when the course is deleted or personal data
  is deleted. grades::restore_missing_grade_backups() copies missing current
  grades back from this table.
- local_gugrades_columnbackup: copy of local_gugrades_column, including the
  original column id. Written when a column is created or its points flag
  changes. Kept when columns are reset or removed, and removed when the
  course is deleted. Restoring grades puts these columns back first so the
  grades backup column ids still match.
- local_gugrades_latest: identifies the current grade record for a course,
  grade item, and user.
- local_gugrades_column: imported or captured grade columns.
- local_gugrades_resit: old-regulation reassessment/resit configuration.
- local_gugrades_resitrequired: users requiring a resit.
- local_gugrades_hidden: hidden grade selections.
- local_gugrades_flag: new-regulation flags, where applicable.

Grade concepts
--------------
- A grade record has a gradetype such as FIRST or SECOND, and may contain a
  numeric rawgrade, a scale value, or an admingrade.
- points indicates whether the grade is numeric points; false indicates a
  scale-style value.
- iscurrent identifies the active record in grade history.
- Provisional/current lookup and latest-grade maintenance are separate concerns;
  inspect both local_gugrades_grade and local_gugrades_latest when changing
  grade lifecycle behaviour.
- CATEGORY is the ordinary aggregated result. CATEGORY1 is an independent
  first-sitting calculation for new-regulation reassessment categories and
  their ancestors. It is current within its own column, but is never selected
  as the latest/provisional grade or released in place of CATEGORY.
- Aggregation carries both results up the category tree. Parents use CATEGORY1
  from children that have it, and the ordinary result from other children.
  Category overrides affect CATEGORY only. Conversion applies independently
  to both results; Nursing conditions are tracked separately. Only the ordinary
  calculation updates displayed drop-low and normalised-weight metadata.
- Single-user recalculation and explanation validate enrolment without loading
  user-display data or requesting external programme/profile synchronisation.
  Repairing missing CATEGORY1 results on page load uses the same calculation path.
- The regulation aggregation method receives a firstsitting boolean after the
  Nursing condition argument. At a reassessment category CATEGORY1 selects the
  earliest-assigned item whose current grade is numeric (including zero) or NS
  (NOSUBMISSION). Order uses the earliest actual assignment ID, including
  historical records and administrative grades such as EC, not the ID of the
  current revision. An early EC becomes eligible if changed to a grade or NS.
  For child categories, order comes from the earliest actual assessment
  assignment in their subtree, never generated category rows. If no available
  current substantive grade exists but EC grades are available, CATEGORY1 uses
  the existing reassessment EC rules as a fallback. A single EC therefore gives
  EC in both totals; once a numeric/NS grade exists it takes precedence over EC
  for first-sitting selection. With neither substantive grades nor EC, CATEGORY1
  reports missing grades. Ancestors
  aggregate the selected results normally. Removing reassessment flags retires unneeded CATEGORY1 rows on the
  next aggregation. CATEGORY1 is excluded from existing capture and history
  views.
- The aggregation page exposes dualgrades for the total and each child column,
  based on the included category tree rather than an individual user's grades.
  Both the page and row-refresh APIs expose displaygrade1st/isadmin1st/error1st
  for totals and display1st/isadmin1st/error1st for children. Missing or
  administrative first-sitting outcomes keep their own display and status.
  Released totals use the stored RELEASED (award) and RELEASED1 (first-sitting)
  snapshots, exposed as releasegrade/releasegrade1st by both APIs. The Released
  heading has matching first-sitting/award subcolumns when the total is dual.
- Aggregation table headers use TanStack column groups: category/item details
  span Grade for a single result, or 1st Sitting and Award for dual results.
  Identity and category details occupy the top row, filters the middle row,
  and Grade/1st Sitting/Award labels a distinct bottom row above the grades.
  The aggregation header uses one blue background with compact metadata and
  controls. The table fills the available width; dual-grade columns stay
  content-sized while names and single-grade columns take the remaining space.
  A shared tint visually joins each first-sitting/award pair. Consistent vertical
  separators divide all columns in the body, filters and grade-label row,
  including each dual-grade pair; top headers span their grouped columns.
  Grade cells retain narrow padding and compact
  filters. Other shared-table layouts keep their usual sizing.
  All assessment/category headers show their percentage when the displayed
  category uses weighted mean, independently of category-only weight-editing
  controls. The header Back button reserves the same title space and action row
  as category headers, aligning it vertically with Expand.
  Aggregation cells anchor menus and grades to the left of their column.
  Administrative grades reserve the same minimum display space as normal
  grade badges, keeping ellipsis controls aligned even for longer messages.
  Invalid aggregation types in category and total headers display "See warning(s)"
  with a subtle yellow highlight instead of "Error"; specific grade-cell error
  messages and aggregation behaviour are unchanged.
  The per-user Reassessment required column is shown only for original
  regulations; the page API exposes showresitrequired and from2026 omits the
  entire column and its controls. Existing stored flags remain unchanged.
  Item/category titles are larger bold plain text. Drillable categories have a
  separate high-contrast Expand button with a chevron and category-specific label.
  A fixed-height action row immediately below every item title keeps navigation
  consistently positioned and metadata aligned; leaf items have no Expand button.
  Title text is truncated visually on one line using the full name, not wrapped
  server-shortened text; the tooltip retains the full name. Space below the title
  row separates the button from grade metadata.
  Assessment information uses a contrasting yellow info button at the top right
  of each item/category header, separate from metadata and navigation. It has a
  descriptive tooltip and accessible label and opens the existing details dialog.
  First-sitting cells are read-only. Award cells retain the existing override,
  visibility, dropped-grade and release behaviour. Sorting and filtering apply
  independently to the displayed result columns. Release and award exports use
  CATEGORY. UPAS uses CATEGORY1 for its First Attempt Grade when dual results
  exist (blank for missing/error outcomes); its Award Grade remains CATEGORY.
  Single-result categories retain the existing UPAS first-attempt rules.
  Duplicate-result read repair, empty-result cleanup and grade-type descriptions
  cover both calculated category types. CATEGORY1 remains non-editable.
- Gradebook grade_items and grade_categories remain Moodle-owned structures.
  local_gugrades refers to them by ID and must account for deleted or changed
  gradebook objects.

Regulations
-----------
The active regulation is selected from the course. Existing code commonly
refers to the original regulation and the from2026 regulation. Do not infer
regulation behaviour from dates alone; use regulations.php and the regulation
classes under regulations/.

Old and new regulation behaviour can differ for:
- exactly-out-of-22 grade items;
- administrative grade codes;
- conversion and display values;
- reassessment/resit configuration.

Tests
-----
Tests are mainly under tests/external and use the advanced test case helpers.
Relevant tests often change course start dates to select a regulation, create
Moodle grade items/categories, write grades through external functions, and
then inspect cleaned external API results.

For a focused PHPUnit run, use the repository's Moodle PHPUnit setup and the
component test filter, for example:

vendor/bin/phpunit --testsuite local_gugrades_testsuite

If that suite is not configured in the local environment, run the specific
file or test class using the repository's normal Moodle PHPUnit command.

Working method
--------------
1. Find the external API or UI entry point.
2. Follow it to the class that computes or mutates the behaviour.
3. Read the nearest test and the relevant database definition.
4. Make the smallest change consistent with existing Moodle patterns.
5. Run the focused test, then broaden validation if the change is shared.
